A compact, calm desktop workspace

Keep the existing forest-green identity and warm neutral surfaces. Shrink the global banner, place identity in the sidebar, and give the task more room. Use a single prominent primary action per form, outlined secondary actions and quiet links. Prefer compact semantic rows for repetitive data and readable cards for recipes.

Use local Segoe UI, 16px body text, 14px secondary text, 28–32px screen titles, 8px spacing steps, 8px control corners, 40px controls and 3px focus outlines. Treat these as CSS dimensions, not dimensions inferred from screenshots. No remote fonts or recipe photos are needed. Icons supplement text labels.

The forest sidebar is the proposed default; board 02 also demonstrates a lighter sidebar variation. Consolidate to one treatment before implementation. Keep the current PantryPal wordmark and tagline; generated leaf marks, slogans and gradients are exploratory decoration, not requests for branding changes.

The native window defaults to 1100 × 760 and can shrink to 640 × 480. These 1536 × 1024 concept images show spacious layouts: at actual sizes, stack recipe columns, let agenda rows grow, use a full-width editing dialog rather than squeezing a drawer, and allow scrolling. At 200% display/text scaling, labels and actions must remain accessible. There is no promise that every populated week always fits without scrolling.

Suggested implementation order

1 · Shared hierarchy

Compact shell, primary/secondary/quiet buttons, consistent headers, local status, field errors and confirmation patterns. Remove stale future-tense copy from measurement settings. Verify contrast and keyboard navigation.

2 · Week and Shopping

Compact agenda and aisle rows, current quantities beside names, consistent status badges and labelled More actions. Retain shopping provenance, alternatives, stale-copy blocking and all adjustments.

3 · Forms and review

Recipe ingredient table and save footer, catalog editor, task-based settings and guided import review. Evaluate the picker’s proposed extra confirmation step before changing its immediate-add behavior.

These are presentation and workflow proposals over the existing domain model. New tabs, drawers and controls need frontend state, focus handling and meaningful flow tests. No migration or change to authoritative measurement/shopping calculations is proposed. Accept individual slices after review; no implementation checklist is marked complete here.

Interaction and safety requirements for implementation

  • Use semantic navigation, headings, tables and labelled inputs. Menus need keyboard operation, Escape handling and focus restoration; neither hover nor drag may be required. Do not hide all essential actions behind unlabeled icons.
  • Retain source wording, entered exact quantities, explicit unit variants, custom-field null semantics and all cooking audit records. Disclosure changes visibility, never persistence.
  • Keep scheduled and actually cooked states distinct. Each repeated meal occurrence retains its own servings, status and ordering. Mark cooked still requires an actual cooked date.
  • Shopping rows retain compatible alternative measures and visible rounding/approximation. Incompatible dimensions, unknown amounts and unconfigured packages stay separate. Badges supplement plain-language reasons.
  • Refresh preserves manual items, amount overrides, checkmarks and exclusions. Changed source identities retain affected adjustments for review; drawer design does not change this policy.
  • Import stays untrusted draft review. Explicit canonical matches and regional-unit decisions remain required where uncertain. Login happens on the website; no new remote capability or extraction technique is proposed.
  • Separate website-data reset from household restore. Merge rejects conflicts; replace removes current records absent from the backup. Both require preview and deliberate confirmation, with recovery backup before changes.
  • Save feedback follows successful persistence. Preserve inputs after failures; confirm draft discard; avoid clearing settings drafts when switching tabs. Keep idempotent retries and stale-revision protection underneath friendlier wording.
  • Update postponement remains possible before installation. Actual downloading/verification/backup/handoff phases control enabled actions. Existing unsaved-work warning remains visible; no automatic installation or unsupported cancellation is proposed.

Inspection evidence and limits

Baseline: DESIGN.md and PLAN.md; working tree was clean at the start. Reviewed App, all feature page/editor/dialog components, shared styles/buttons, typed IPC, native window sizing and local capability scope. Historical native captures inspected: phase4-week, phase5-shopping, phase3-meals, ingredient-modal-open, phase6-import and phase2-settings.

Discrepancies identified: historical screenshots include earlier “coming later” behavior; current source implements those workflows. MeasurementSettings still says compatible aggregation is available “when grocery generation is available,” despite Phase 5 completion. The intentional proposal is to update that copy in a later implementation slice, retaining current behavior. DESIGN remains the baseline. No scope or architecture changes were silently applied.

Generation: built-in image_gen via the imagegen skill, ten original calls and three targeted corrections. Final prompt set is in prompts.json; corrections are in corrections.json. Final PNGs are in mockups/. Original outputs were copied into the repository; discarded variants are not included.

Checks: npm run typecheck passed. Final HTML/JSON formatting, local image-link/PNG checks and git diff --check are recorded in verification.txt. No application behavior was changed; Rust tests, native build and new UI flow tests were not run for this artifact-only slice.

Not verified: live clicking, focus behavior, screen-reader use, exact render at native window sizes and installed-app visual equivalence. Browser discovery returned no available browser. Artwork was visually reviewed, but it is not an accessibility audit or a pixel-accurate implementation specification. Remaining generated details are called out beneath each board.

Plan: release phase dashboard and acceptance checkboxes remain unchanged. Next unchecked release tasks concern deferred clean-machine testing and published-feed acceptance; neither is part of this requested review.
